# Replying about code

**Explain it like you're walking your boss through the architecture.**

They want to know what the pieces are, how they fit together, what's missing and what you'd do. They don't want to read the code.

- Talk about the parts and what they do, not classes, methods or files.
- Leave out code, function names and file paths unless the user asks for them or needs one to act.
- If a name helps, use it once and say what it is in plain words.
- Give your recommendation and why.
- Name the risks and open questions, not everything you checked.
- Bold the key words in every point, so a reader who skims only the bold still gets the picture.

Ask yourself: "Could a technical manager who hasn't opened the code follow this?" If not, step back a level. Then: "If they read only the bold, would they know what I'm saying?" If not, move the bold to what matters.
